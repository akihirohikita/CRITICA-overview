# CRITICA

> **構造で残す。文化に頼らない。**
> 現場知・暗黙知・運用ノウハウを、捉え、構造化し、保存し、継承するための AI 知識インフラ。

CRITICA は、散在するドキュメント、マルチメディア記録、専門家との対話、日々の気づき、改善提案を、組織の業務構造そのものに紐付いた、検索可能で進化し続ける知識へと変換します。

---

## CRITICA がやっていること

CRITICA は、すべての知識を、それが属する業務構造に紐付けます。

**フレームワーク → フェーズ → カテゴリ → プロセス → ステップ**

つまり AI は、ドキュメントから答えるのではありません。
**業務の構造に紐付いた知識から答える** のです。

### 具体例

40 年の経験を持つ刀匠が引退するとします。

- **一般的な RAG ツール**: 彼へのインタビュー記録を保存します。AI は質問されればその内容を引用できます。
- **CRITICA**: 彼の知識を、彼が実際に行っていた **プロセス → ステップ** に紐付けます。Human Expert Query (HEQ) ワークフローで検証します。γ/Ω に基づく構造的指標を通じて、運用上の適合度を評価可能な設計になっています。そして、次の作業者がまさにそのステップに立ったその瞬間に — キーワード検索を誰かが思いつくのを待つのではなく — 知識を提示します。

知識はただ「どこかに存在する」のではありません。
**正しい場所に、正しい時に、正しい構造的文脈で立ち上がってくる。**

---

## なぜ単なる RAG ではダメなのか

世の中の「AI 知識管理」プロダクトの多くは、ドキュメントストレージに RAG チャットを被せたものです。テキストを検索することはできますが、業務を理解しているわけではありません。

CRITICA はまったく別の前提に立っています。

| 一般的な RAG | CRITICA |
|---|---|
| 知識 = ドキュメント | 知識 = プロセスに紐付いたドキュメント |
| キーワード類似度で検索 | 実業務における構造的位置で検索 |
| 一問一答で完結 | 訂正と改善のループが回り続ける |
| AI が単独で動く | 人間専門家による検証ゲートを組み込む |
| データが蓄積する | 知識が **構造化** される |

哲学の出所は、政策研究大学院大学 (GRIPS) の室田教授の言葉です:
> 文化や個人に依存するな。**知識を構造に埋め込め。**

## 主要機能

- **マルチチャネル知識収集** — テキスト、音声、画像、タイムスタンプ付き動画再生、モバイル現場収集
- **プロセス / ステップベースの知識構造化** — すべてのナレッジが、自分の居場所を知っている
- **RAG ベースの AI チャット** — 単なるテキスト類似度ではなく、業務構造に基づいて応答
- **Human Expert Query (HEQ) ワークフロー** — バイリンガル翻訳、フォローアップ機能、専門家検証ゲート
- **KAIZEN 提案ワークフロー** — ボトムアップの改善提案が、死蔵される議事録ではなく、作業指示書 (Work Order) に直結する
- **日報と運用ログ** — 組織学習の基礎レイヤー
- **Telegram ベースの現場知識収集** — 現場から音声/写真を即時投入、AI が要点抽出、専門家がレビュー
- **知識訂正・回答訂正フロー** — AI が間違えたとき、構造そのものが学習する
- **Knowledge Relevance Calibration (KRC)** — どの知識が実際に役に立っているかを、フィードバック駆動でスコアリング
- **Knowledge Emergence Graph (KEG)** — 組織の知識がどう形成され、繋がり、進化するかを可視化
- **マルチテナントアーキテクチャ** — 組織ごとに完全分離、スーパーアドミンによる横断検索も可能
- **三層運用構造** — 日報 → 作業指示書管理 → 経営者ビュー

## 想定ユースケース

CRITICA は、**構造的な知識喪失** に直面している組織に特に有効です:

- 製造業の技能伝承
- 伝統工芸・職人技の保存
- プラント運用・保全
- 現場作業者向けトレーニングプログラム
- 農業・酪農の運用知識
- 企業内の知識インフラ
- 世代を跨いだ事業承継

組織にとって最も価値のある専門性が、ごく数名の頭の中にしか存在せず、その人が辞めると同時に外に流れ出てしまう — そんな問題に対して、CRITICA は設計されています。

## 開発規模

たった **3 ヶ月強** の期間で、ファウンダー 1 人が Claude (Anthropic — Opus + Sonnet) と協働して構築しました。

| 指標 | 数値 |
|---|---|
| アプリケーションコード | **153,154 行** |
| アーキテクチャ・設計ドキュメント | **166,504 行** |
| ソースファイル数 (TypeScript / Python) | **473 ファイル** |
| プロジェクトファイル総数 | **940 ファイル** |
| 平均日産コード行数 | **約 1,700 行 / 日** |

**ドキュメントの総量がコードの総量を上回っている**ことに注目してください。

これは偶然ではありません。CRITICA 自身の哲学を、CRITICA の開発プロセスそのものに再帰的に適用した結果です:

> **構造が先。コードはその後。**
>
> 設計判断が文書に残されていなければ、それは存在しないのと同じです —
> 次の開発者にとっても、次のセッションにとっても、半年後の自分にとっても。

CRITICA は、CRITICA が世に問おうとしている原則そのものを使って構築されています。

## 技術スタック

- **フロントエンド**: TypeScript / React
- **バックエンド**: Python / FastAPI
- **インフラ**: Google Cloud Run、Firebase Hosting、Firestore、Cloud Storage
- **LLM**: **Claude API (Anthropic)** — チャット、要点抽出、翻訳、構造解析の中核推論エンジン
- **埋め込み・音声**: OpenAI (text-embedding、Whisper)
- **メール**: Resend (受信・送信両方向)
- **マルチモーダル取り込み**: テキスト、音声 (文字起こし付き)、画像 (Vision 解析付き)、動画 (タイムスタンプ再生付き)
- **CI/CD**: GitHub Actions + Workload Identity Federation、ステージング環境への完全自動デプロイ

## ファウンダー兼開発者について

CRITICA は **疋田 彰宏 (Akihiro Hikita)**、合同会社 COSIMO 代表が開発しています。

彼の本来の専門領域は、ソフトウェアエンジニアリングではなく **上流工程のビジネスフロー設計** です。CRITICA は、Claude (Anthropic) との深い協働によって構築されており、**ドメイン知識がアーキテクチャを駆動し、AI がバージョン管理された明文ルールの下で実装規律を担う** という、新しい AI 拡張ソロ開発モデルを体現しています。

CRITICA は、これらの問題に最初に直面したとき、「こういうものがあったらよかったのに」と思った、そのシステムそのものです。
